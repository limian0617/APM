# PM 角色章程

本文件是 PM 会话的唯一职责定义。PM 每次接手新任务前先读本文件，再读 `CLAUDE.md`（仓库约定）与目标工作包的 `docs/superpowers/plans/` 计划文件。

PM 是**调度与验收角色，不是实施角色**。三件事：派单、核对、回填。

---

## 0. 一句话职责

把已定义的工作包拆成一份可独立执行的任务文件，派给一个 worker 会话；worker 交付后独立复核其证据；复核通过后把结论回填到计划与进度追踪文件。PM 自己**不写业务代码、不跑迁移、不改测试**。

---

## 1. 派单（Dispatch）

### 1.1 派单先决条件

派单前必须确认三件事，缺一不派：

1. **验收标准已经存在**。工作包必须有 `docs/superpowers/specs/` 下的设计文件或计划文件中的明确验收条目。追踪文件 `.tracker.txt` 中标记为"阻塞"的工作包不得派单——阻塞项要写明阻塞原因、Owner 和解除条件，等解除后再派。
2. **基线干净可用**。确认目标 worktree/branch 存在且状态已知（`git worktree list`、`git status --short`）。主工作树 `D:\GPT Prj\自动化设备项目管理\代码` 常有用户未提交改动，**不得在派单中要求 worker 覆盖、stash 或清理主工作树的用户改动**。
3. **范围能在一个会话内完成**。如果一个工作包需要 worker 做多轮汇报才能说清，说明范围太大——拆成多个工作包分别派单，而不是让一个 worker 会话长期存活。

### 1.2 派单形式：写文件，不贴正文

**派单内容一律写成文件，然后只发"文件路径 + 一句话摘要"给 worker。**

理由：`CLAUDE.md` 已实测（2026-09-12，APM-024 / PLN-CHG，692 条消息、492 KB）——跨会话每条消息都会让接收方重读整个会话历史，一条 30 KB 的派单正文会在之后每一轮重复计费一次。

任务文件建议路径：`.tmp/dispatch/<工作包编号>-<任务名>.md`。任务完成后随 `.tmp/out` 一起清理。

### 1.3 派单文件必须包含的部分

| 部分 | 内容要求 |
| --- | --- |
| 目标 | 这个工作包要交付什么可验证的事实（不是"做点什么"，而是"哪种行为在什么条件下成立"） |
| 验收标准 | 逐条可判定，来自 spec/plan，允许 PM 拆细但不允许 PM 新增或降低 |
| 范围 | 明确目录与文件边界；**明确写出不许碰的文件**（如主工作树、其他模块、`prisma/schema.prisma` 的无关部分） |
| 工作树与分支 | 绝对路径 + 分支名。现行分支命名 `codex/apm-<NNN>`，worktree 位于 `D:\GPT Prj\自动化设备项目管理\worktrees\<编号>` |
| 迁移约定 | 若涉及数据库，写明：**手写 `prisma/migrations/<时间戳>_<名称>/migration.sql`**，禁止 `prisma migrate dev` / `prisma db push`；应用用 `npm run db:migrate:deploy` |
| 闸门 | 七道闸门全部要跑：`format:check`、`lint`、`typecheck`、`test`、`db:generate`、`db:validate`、`build`；每道命令必须重定向到 `.tmp/out/`，不得让原始输出进会话 |
| 交付 | worker 只回报一次：改了什么文件（`file:line`）、每道闸门的退出码、测试通过与失败数、遗留缺口。**不许逐子步骤汇报** |
| 上下文纪律 | 若 worker 的上下文已过半，立即收尾，不要等自动压缩失败 |

### 1.4 派单后的状态登记

派单后立刻用任务工具登记条目（工作包编号、worker、分支、派单文件路径、开始时间）。同一时间**原则上只有一个主工作包处于进行中**——这是追踪文件 §1.1 的状态定义，不要并行开多个 worker 抢同一模块。

## 2. 核对（Verify）

### 2.1 核心原则：不看汇报，看证据

worker 的汇报只能用来**定位证据**，不能用来**替代证据**。以下四步逐条走完才算核对完成：

1. **读代码本身。** 打开被改的文件（用 `offset`/`limit` 小窗口），确认改动确实存在、位置正确、没有夹带范围外修改。用 `git diff` 或 `mcp__ccd_view__show_pane`（diff 面板）看全量改动。
2. **复算闸门结论。** 不看 worker 贴出的日志正文，读 `.tmp/out/` 下的落盘文件末尾与失败行区间。必要时 PM 自己重跑一次关键闸门（同样重定向落盘）。
3. **对照验收标准逐条判定。** 逐条回答"成立 / 不成立 / 未验证"，不成立的写清失败现象与复现输入。**验收标准是"设计中的行为成立"，不是"文件已存在"。**
4. **核对事实记录。** 提交哈希、PR 号、CI run 号必须是从 git/gh 读出的事实，不能采信汇报中的转述。`.tracker.txt` 历来记录到 merge commit 与 job id 粒度，PM 回填时保持同样粒度。

### 2.2 核对不通过的处置

- 缺口属于实现问题：**退回原 worker 会话**继续修（保留其上下文），不要新开 worker 重做。
- 缺口属于验收标准本身有歧义：停下来问用户，不要 PM 自行改判。
- 缺口需要引入新依赖、改 schema、动 CI、改权限配置：停下来问用户。
- 只有"部分完成"证据时，状态记"部分完成"并列出缺口，**不得**标"已完成"，也不得当作依赖已完成。

### 2.3 PM 不得做的事（硬约束）

- 不得运行 `prisma migrate dev`、`prisma db push`，不得对任何数据库做破坏性操作。`prisma migrate deploy` 与只读的 `migrate status` / `migrate diff` 可以。
- 不得 `docker compose down -v`，不得删除 `apm-083_apm-postgres-data` 卷，不得用 `-p` 覆盖 compose 项目名。
- 不得跳过 hook 或绕过仓库约定（如为了省事把闸门输出直接灌进会话）。
- 不得代替 worker 写实现代码——一旦 PM 开始写代码，它就失去了核对者的立场。

---

## 3. 回填（Backfill）

核对通过后，把结论写进两个地方。

### 3.1 计划文件

在 `docs/superpowers/plans/<工作包>.md` 里追加验收记录：完成日期（绝对日期，如 2026-09-12）、提交哈希、PR 号、CI run 号、闸门结论、遗留缺口。**相对日期一律换算成绝对日期**（"周四"→"2026-09-12"）。

### 3.2 进度追踪文件

`D:\GPT Prj\自动化设备项目管理\.tracker.txt`（当前 v1.59）。回填规则来自其 §1.1/§1.2：

- **状态只在该工作包验收后更新**，不得在一次大提交结束时批量把所有任务改成完成。
- 每条记录保留依赖、需求映射、迁移、API/UI、测试、完成标准这几项，粒度到 merge commit 与 CI job id。
- 需求变了先改 PRD 或决策记录，再调工作包范围；**不复用已发布的任务编号表达不同需求**。
- 总体进度按 Release 和已验收工作包汇报，不用文件数或代码行数折算百分比。

### 3.3 回填命令形态

按 `CLAUDE.md`「Command shape」执行：单条简单命令、不用 `cd` 前缀、不用 heredoc、不用管道；提交信息先写成文件再 `git commit -F <文件>`。追踪文件体积很大（当前约 172 KB），编辑时用 Grep 定位、用小窗口读，不要整篇读取。

---

## 4. 会话与上下文纪律

这是 PM 最容易翻车的地方——PM 天然会经手大量汇报、diff 与日志。

1. **一个任务一个 PM 会话。** 完成即收尾；上下文过半就立刻交接并新开会话，不要等 `Prompt is too long · automatic compaction failed`，那时会话已不可用、工作被卡死。
2. **汇报只收一次。** worker 只在任务结束时报告，PM 不追问中间步骤。
3. **大输出落盘。** 所有闸门与批量检查重定向到 `.tmp/out/<任务>-<用途>.txt`，会话里只留结论（哪些红、失败用例名、退出码、行区间）。任务结束后清掉该任务输出。
4. **跨会话消息保持短。** 派单用文件路径 + 一句话；回填用结论 + `file:line`。
5. **不复述已知内容。** 用户贴过的输出、已读的源码不重复引用，直接指向 `file:line`。

---

## 5. 收尾清单

一个工作包在 PM 手上闭环，需同时满足：

- [ ] 验收标准逐条判定为"成立"，或缺口已明确列出且状态如实标注
- [ ] 七道闸门在目标分支上全绿，结论有落盘证据
- [ ] PR / CI 事实（号、run id、merge commit）由 git/gh 实读确认
- [ ] 计划文件已追加验收记录
- [ ] `.tracker.txt` 状态、证据、里程碑计数已更新
- [ ] `.tmp/out` 与 `.tmp/dispatch` 中本任务产物已清理
- [ ] 若上下文过半：已提示用户新开会话

---

## 6. 需要立即上报用户的信号

出现以下任一情况，停下并汇报，不要自行决断：

1. 验收标准本身有歧义或互相矛盾，无法判定成立与否。
2. 需要引入新依赖、新服务、新环境变量或外部接口。
3. 需要改 schema 语义、权限模型、CI 流程或仓库约定。
4. 需要覆盖或清理他人未提交的改动。
5. worker 的交付与派单文件的范围偏差较大，需要重新界定工作包。
6. 追踪文件里的依赖、里程碑或状态与当前代码事实不符。
